# 再設計実装 — ADR からの逸脱ログ

**対象**: ADR 0004 / 0005 / 0006 / 0007 / 0008 の実装（移行計画ステップ2〜5）
**方針**: ADR と現実が矛盾した場合、勝手な設計変更はせず、**最小の逸脱**を選んでここに記録する。

各エントリの形式:

- **逸脱**: 何を ADR と違えたか
- **ADR の記述**: 該当箇所
- **理由**: なぜ ADR どおりにできなかったか
- **影響範囲**: 何が ADR の想定と変わるか
- **原状回復**: ADR どおりに戻すなら何が必要か

---

## L-001: 検証基盤に「既知違反レジストリ」を導入した

- **逸脱**: ADR 0008 §6 は全 fixture に対し `format(format(x)) == format(x)` を CI で強制すると定めるが、
  移行中は旧実装が既知の違反（F3）を持つため、`tests/invariants.rs` に
  `known_violations` レジストリを設け、列挙されたものだけを許容する形にした。
- **ADR の記述**: ADR 0008 §6「検証: 全 fixture + 実コーパスに対し … を CI で強制する」
- **理由**: 検証基盤を新実装より**先行**して入れる（完了条件1）と、旧実装ではテストが赤になり、
  CLAUDE.md の「コミット前に `cargo test -q` を通す」規約と両立しない。
  レジストリはエントリ追加を許さず、逆に「直ったのに登録されたまま」も失敗にするため、
  弱い許容ではなく**単調に減る移行台帳**として機能する。
- **影響範囲**: 移行完了時点で `known_violations` の両配列が空になることが完了条件。
  空になった時点で ADR 0008 §6 の要求と完全一致する。
- **原状回復**: レジストリごと削除する（配列が空なら挙動は同一）。

## L-002: 意味保存テストの「re-lex」をパーサ経由で行っている

- **逸脱**: ADR 0008 §6 は「入力と出力を re-lex してトリビア以外のトークン列が一致」を求めるが、
  実装は `parse_perl` して CST の葉トークンを比較している。
- **ADR の記述**: ADR 0008 §6 (b)
- **理由**: 現行 lexer は parser 駆動（`LexContext` を呼び出し側が与える）であり、
  parser なしに単体で「そのファイルのトークン列」を確定できない。
  ADR 0005 の新 lexer も `expect` を parser が設定する設計なので、この性質は移行後も残る。
  したがって「re-lex」の忠実な実装は「再パースして葉トークンを読む」になる。
- **影響範囲**: なし（検出能力は同等。F1 のような内容改変は同じく検出される）。
  ただしトークン列の差が「lexer の差」か「parse 形状の差」かは区別されない。
- **原状回復**: 不要（ADR の意図をこの環境で実現した形）。

## L-003: ビット演算子の優先順位は perlop どおり「比較より下」に置いた

- **逸脱**: ADR 0007 §4 は「ビット演算子（`& | ^`）を比較演算子より**上**（強く結合）に置く」と
  書いているが、実装は perlop どおり**比較より下**（`==` 等より弱く、`&&` より強い）に置いた。
- **ADR の記述**: ADR 0007 §4 第1項
- **理由**: 同じ文が「既知の誤りを **perlop に合わせて**修正する」と述べており、
  括弧内の指示はその目的と矛盾する。perlop の優先順位は（強い順に）
  `<< >>` → named unary → 関係演算子 → 等価演算子 → `&` → `| ^` → `&&` → `|| //` であり、
  ビット演算子は比較より**下**である。
  さらに現行 `src/parser/expression/precedence.rs:21-25` は
  COMPARISON=40 / BITWISE_AND=39 / XOR=38 / OR=37 と、すでに perlop どおりであった。
  ADR が「既知の誤り」と呼んでいる対象は、実際には誤っていない。
  括弧内の指示に従うと perlop と異なる木ができ、ADR 自身の目的に反するため、
  最小の逸脱として「§4 の目的（perlop 準拠）を採り、括弧内の方向指示を採らない」を選んだ。
- **影響範囲**: `$a & $b == $c` の結合。perlop では `$a & ($b == $c)`。
  ADR の括弧に従えば `($a & $b) == $c` になっていた。既存 fixture に該当例はない。
- **原状回復**: `precedence.rs` 相当のテーブルで BITWISE_* を EQUALITY より上に移すだけ。
  ただしその場合 perlop と非互換になる。
- **未解決**: ADR 0007 §4 の当該記述自体を訂正すべきだが、ADR の改訂は本作業の
  スコープ外としてここに記録するにとどめる。

## L-004: parser スナップショットの差分分類は「全件が形状変更」に潰れる

- **逸脱**: 完了条件6（およびに移行計画ステップ3）は、スナップショット差分を
  「CST 形状変更 / 意図的挙動変更 / バグ修正」に分類し、分類ごとに独立コミットせよと言う。
  これを **formatter 出力スナップショットにのみ**適用し、parser スナップショットは
  「全 78 本が CST 形状変更」という単一の事実として扱う。
- **移行計画の記述**: 評価ノート §5 ステップ3、完了条件6
- **理由**: 新 parser はノード語彙そのものが別である（旧 `SyntaxKind` の flat enum と
  新 `NodeKind`）。ADR 0007 §2 が定める正規形（`STMT` ラッパー廃止、
  `FUNCTION_CALL_EXPR` の4分割、`LIST_EXPR` の常時生成、演算子クラスの分離）により、
  parser スナップショットは1本残らず全面的に変わる。
  行単位の差分は取れるが、そこから「意図的挙動変更」と「バグ修正」を読み分けることは
  できない。分類に情報がない以上、分類する意味がない。
- **影響範囲**: 分類レポートの対象が formatter 出力に限られる。
  parser 側は「ADR 0007 §2 の正規形への一括移行」1件として記録する。
- **原状回復**: 不要（分類そのものが定義できないため）。

## L-005: 名前を読む位置のために lexer に `take_name` を足した

- **逸脱**: ADR 0005 §2 は expect を `Term` / `Operator` の2状態に限る。
  実装ではこれに加えて、parser が「ここは名前である」と lexer に伝える
  `Lexer::take_name()` を設けた。
- **ADR の記述**: ADR 0005 §2「`pub enum Expect { Term, Operator }`」
- **理由**: 名前が来る位置（`sub` の直後、`package` の直後、`->` の直後）は
  2状態のどちらでも正しく表現できない。
  - `Term` では `sub tr {}` の `tr` が置換演算子を開く。
  - `Operator` では `sub x100 {}` の `x100` が `x` + `100` に割れる
    （ADR 0005 §5 が定める `"abc"x5` の規則の副作用）。
  ADR 0005 §5 は「直前トークンが `->` の場合はメソッド名なので parser が
  expect=Operator にしている」と書いており、名前位置を Operator で代用する想定だが、
  `x` 分割規則と両立しない。
- **選んだ最小の逸脱**: 3つ目の expect 状態を作らず、
  「その位置のトークンを識別子として読む」という1回限りの命令を lexer API に足した。
  これは ADR 0004 §5 の「kind 付き raw span トークン」（prototype の
  `take_raw_parens` と同型）の一種であり、
  強制は ADR 0007 §5 が要求するとおり `grammar::name()` の1箇所のみ。
- **影響範囲**: `sub` / `package` / メソッド名 / ハッシュキーの位置で、
  キーワードが常に IDENT として木に入る。制御フローの
  `return` / `next` / `last` / `redo` / `goto` は意図的に除外し、
  キーワードトークンのまま残している。
- **原状回復**: expect に `Name` を足して3状態にすれば API からは消える。
  ただし ADR 0005 §2 の「2状態」という明示に反する。

## L-006: `DelimiterTightness` / `AlignmentStrategy` オプションを移植しなかった

- **逸脱**: 旧 `FormatterOptions` にあった `DelimiterTightness`（デリミタ内側の空白）と
  `AlignmentStrategy` を新 formatter に移植せず、対応する
  `tests/delimiter_tightness.rs` を削除した。
- **移行計画の記述**: 評価ノート §5 ステップ5「新旧切り替え後、旧実装を削除」
  （オプションの扱いには言及がない）
- **理由**: ADR 0008 §7 はレンダラのパラメータとして「インデント幅・タブ等」しか
  挙げておらず、デリミタ内側の空白は build 時の spacing 規則
  （`Doc::Space` を置くかどうか）の一部である。オプションとして残すと、
  ADR 0008 §2 が消したはずの「spacing の分岐が2箇所にある」状態が戻る。
- **影響範囲**: `[ 1, 2 ]` → `[1, 2]`、`$h->{ key }` → `$h->{key}` に統一される。
  分類レポート §2.2 に記録した。
- **原状回復**: オプションではなく `wants_space` の分岐として再導入する。
  `FormatterOptions` を build 側に渡す配線はすでにある。

## L-007: 検証対象から `errors/` fixture を除外している

- **逸脱**: `tests/invariants.rs` は `src/parse/fixtures/errors/` と
  `src/parse/fixtures/statements/errors/` を検査対象に含めない。
- **ADR の記述**: ADR 0008 §6「全 fixture + 実コーパスに対し … を CI で強制する」
- **理由**: これらは「壊れた入力が何を報告するか」を固定するための fixture であり、
  診断が出ることが期待される挙動である。「診断なしでパースされること」を
  要求すると定義上必ず失敗する。
  なお冪等性は `src/fmt/tests.rs` の `malformed_input_still_formats_to_a_fixed_point`
  で別途検査している。
- **影響範囲**: 検査対象は 76 本（fmt 47 + parse success 29）。
- **原状回復**: 不変条件ごとに対象集合を分ける（診断なしは success のみ、
  冪等性と可逆性は全件）。現状は前者に合わせて一律に絞っている。
