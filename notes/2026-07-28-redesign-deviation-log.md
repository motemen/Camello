# 再設計実装 — ADR からの逸脱ログ

**対象**: ADR 0004 / 0005 / 0006 / 0007 / 0008 の実装（移行計画ステップ2〜5）
**方針**: ADR と現実が矛盾した場合、勝手な設計変更はせず、**最小の逸脱**を選んでここに記録する。

各エントリの形式:

- **逸脱**: 何を ADR と違えたか
- **ADR の記述**: 該当箇所
- **理由**: なぜ ADR どおりにできなかったか
- **影響範囲**: 何が ADR の想定と変わるか
- **原状回復**: ADR どおりに戻すなら何が必要か

---

## L-001: 検証基盤に「既知違反レジストリ」を導入した

- **逸脱**: ADR 0008 §6 は全 fixture に対し `format(format(x)) == format(x)` を CI で強制すると定めるが、
  移行中は旧実装が既知の違反（F3）を持つため、`tests/invariants.rs` に
  `known_violations` レジストリを設け、列挙されたものだけを許容する形にした。
- **ADR の記述**: ADR 0008 §6「検証: 全 fixture + 実コーパスに対し … を CI で強制する」
- **理由**: 検証基盤を新実装より**先行**して入れる（完了条件1）と、旧実装ではテストが赤になり、
  CLAUDE.md の「コミット前に `cargo test -q` を通す」規約と両立しない。
  レジストリはエントリ追加を許さず、逆に「直ったのに登録されたまま」も失敗にするため、
  弱い許容ではなく**単調に減る移行台帳**として機能する。
- **影響範囲**: 移行完了時点で `known_violations` の両配列が空になることが完了条件。
  空になった時点で ADR 0008 §6 の要求と完全一致する。
- **原状回復**: レジストリごと削除する（配列が空なら挙動は同一）。
- **解決（2026-07-30 追記）**: 移行完了時に空になり、レジストリは削除した。その後、
  台帳そのものが移行専用の仕組みではないと判断して再導入した
  （`src/fmt/fixtures/regressions/known-broken.txt`）。理由は移行時と同じ構造で、
  「まだ直っていない欠陥を、直った日ではなく見つかった日にツリーへ入れる」ためには
  記録する場所が要る。単調性（追加不可・直ったら削除を強制）もそのまま。
  ADR 0008 §6 との関係も移行時と同じで、台帳が空のとき要求と完全一致する。

## L-002: 意味保存テストの「re-lex」をパーサ経由で行っている

- **逸脱**: ADR 0008 §6 は「入力と出力を re-lex してトリビア以外のトークン列が一致」を求めるが、
  実装は `parse_perl` して CST の葉トークンを比較している。
- **ADR の記述**: ADR 0008 §6 (b)
- **理由**: 現行 lexer は parser 駆動（`LexContext` を呼び出し側が与える）であり、
  parser なしに単体で「そのファイルのトークン列」を確定できない。
  ADR 0005 の新 lexer も `expect` を parser が設定する設計なので、この性質は移行後も残る。
  したがって「re-lex」の忠実な実装は「再パースして葉トークンを読む」になる。
- **影響範囲**: なし（検出能力は同等。F1 のような内容改変は同じく検出される）。
  ただしトークン列の差が「lexer の差」か「parse 形状の差」かは区別されない。
- **原状回復**: 不要（ADR の意図をこの環境で実現した形）。

## L-003: ビット演算子の優先順位は perlop どおり「比較より下」に置いた

- **逸脱**: ADR 0007 §4 は「ビット演算子（`& | ^`）を比較演算子より**上**（強く結合）に置く」と
  書いているが、実装は perlop どおり**比較より下**（`==` 等より弱く、`&&` より強い）に置いた。
- **ADR の記述**: ADR 0007 §4 第1項
- **理由**: 同じ文が「既知の誤りを **perlop に合わせて**修正する」と述べており、
  括弧内の指示はその目的と矛盾する。perlop の優先順位は（強い順に）
  `<< >>` → named unary → 関係演算子 → 等価演算子 → `&` → `| ^` → `&&` → `|| //` であり、
  ビット演算子は比較より**下**である。
  さらに現行 `src/parser/expression/precedence.rs:21-25` は
  COMPARISON=40 / BITWISE_AND=39 / XOR=38 / OR=37 と、すでに perlop どおりであった。
  ADR が「既知の誤り」と呼んでいる対象は、実際には誤っていない。
  括弧内の指示に従うと perlop と異なる木ができ、ADR 自身の目的に反するため、
  最小の逸脱として「§4 の目的（perlop 準拠）を採り、括弧内の方向指示を採らない」を選んだ。
- **影響範囲**: `$a & $b == $c` の結合。perlop では `$a & ($b == $c)`。
  ADR の括弧に従えば `($a & $b) == $c` になっていた。既存 fixture に該当例はない。
- **原状回復**: `precedence.rs` 相当のテーブルで BITWISE_* を EQUALITY より上に移すだけ。
  ただしその場合 perlop と非互換になる。
- **未解決**: ADR 0007 §4 の当該記述自体を訂正すべきだが、ADR の改訂は本作業の
  スコープ外としてここに記録するにとどめる。

## L-004: parser スナップショットの差分分類は「全件が形状変更」に潰れる

- **逸脱**: 完了条件6（およびに移行計画ステップ3）は、スナップショット差分を
  「CST 形状変更 / 意図的挙動変更 / バグ修正」に分類し、分類ごとに独立コミットせよと言う。
  これを **formatter 出力スナップショットにのみ**適用し、parser スナップショットは
  「全 78 本が CST 形状変更」という単一の事実として扱う。
- **移行計画の記述**: 評価ノート §5 ステップ3、完了条件6
- **理由**: 新 parser はノード語彙そのものが別である（旧 `SyntaxKind` の flat enum と
  新 `NodeKind`）。ADR 0007 §2 が定める正規形（`STMT` ラッパー廃止、
  `FUNCTION_CALL_EXPR` の4分割、`LIST_EXPR` の常時生成、演算子クラスの分離）により、
  parser スナップショットは1本残らず全面的に変わる。
  行単位の差分は取れるが、そこから「意図的挙動変更」と「バグ修正」を読み分けることは
  できない。分類に情報がない以上、分類する意味がない。
- **影響範囲**: 分類レポートの対象が formatter 出力に限られる。
  parser 側は「ADR 0007 §2 の正規形への一括移行」1件として記録する。
- **原状回復**: 不要（分類そのものが定義できないため）。

## L-005: 名前を読む位置のために lexer に `take_name` を足した

- **逸脱**: ADR 0005 §2 は expect を `Term` / `Operator` の2状態に限る。
  実装ではこれに加えて、parser が「ここは名前である」と lexer に伝える
  `Lexer::take_name()` を設けた。
- **ADR の記述**: ADR 0005 §2「`pub enum Expect { Term, Operator }`」
- **理由**: 名前が来る位置（`sub` の直後、`package` の直後、`->` の直後）は
  2状態のどちらでも正しく表現できない。
  - `Term` では `sub tr {}` の `tr` が置換演算子を開く。
  - `Operator` では `sub x100 {}` の `x100` が `x` + `100` に割れる
    （ADR 0005 §5 が定める `"abc"x5` の規則の副作用）。
  ADR 0005 §5 は「直前トークンが `->` の場合はメソッド名なので parser が
  expect=Operator にしている」と書いており、名前位置を Operator で代用する想定だが、
  `x` 分割規則と両立しない。
- **選んだ最小の逸脱**: 3つ目の expect 状態を作らず、
  「その位置のトークンを識別子として読む」という1回限りの命令を lexer API に足した。
  これは ADR 0004 §5 の「kind 付き raw span トークン」（prototype の
  `take_raw_parens` と同型）の一種であり、
  強制は ADR 0007 §5 が要求するとおり `grammar::name()` の1箇所のみ。
- **影響範囲**: `sub` / `package` / メソッド名 / ハッシュキーの位置で、
  キーワードが常に IDENT として木に入る。制御フローの
  `return` / `next` / `last` / `redo` / `goto` は意図的に除外し、
  キーワードトークンのまま残している。
- **原状回復**: expect に `Name` を足して3状態にすれば API からは消える。
  ただし ADR 0005 §2 の「2状態」という明示に反する。

## L-006: `DelimiterTightness` / `AlignmentStrategy` オプションを移植しなかった

- **逸脱**: 旧 `FormatterOptions` にあった `DelimiterTightness`（デリミタ内側の空白）と
  `AlignmentStrategy` を新 formatter に移植せず、対応する
  `tests/delimiter_tightness.rs` を削除した。
- **移行計画の記述**: 評価ノート §5 ステップ5「新旧切り替え後、旧実装を削除」
  （オプションの扱いには言及がない）
- **理由**: ADR 0008 §7 はレンダラのパラメータとして「インデント幅・タブ等」しか
  挙げておらず、デリミタ内側の空白は build 時の spacing 規則
  （`Doc::Space` を置くかどうか）の一部である。オプションとして残すと、
  ADR 0008 §2 が消したはずの「spacing の分岐が2箇所にある」状態が戻る。
- **影響範囲**: `[ 1, 2 ]` → `[1, 2]`、`$h->{ key }` → `$h->{key}` に統一される。
  分類レポート §2.2 に記録した。
- **原状回復**: オプションではなく `wants_space` の分岐として再導入する。
  `FormatterOptions` を build 側に渡す配線はすでにある。
- **解決（2026-07-28 追記）**: ユーザーの要望により再導入した。この項の方針どおり
  build 時の spacing 分岐として実装（`FormatterOptions::delimiter_spacing`、
  `tight` / `standard` / `loose`、既定 `standard` = 旧 SPACING-7 準拠。丸括弧は常に tight）。
  あわせて `min_spaces_before_comment` の既定を 1 → 4（旧実装の perltidy 風の見た目）に変更。
  formatting.md SPACING-7 / COMMENT-3 も更新済み。

## L-007: 検証対象から `errors/` fixture を除外している

- **逸脱**: `tests/invariants.rs` は `src/parse/fixtures/errors/` と
  `src/parse/fixtures/statements/errors/` を検査対象に含めない。
- **ADR の記述**: ADR 0008 §6「全 fixture + 実コーパスに対し … を CI で強制する」
- **理由**: これらは「壊れた入力が何を報告するか」を固定するための fixture であり、
  診断が出ることが期待される挙動である。「診断なしでパースされること」を
  要求すると定義上必ず失敗する。
  なお冪等性は `src/fmt/tests.rs` の `malformed_input_still_formats_to_a_fixed_point`
  で別途検査している。
- **影響範囲**: 検査対象は 76 本（fmt 47 + parse success 29）。
- **原状回復**: 不変条件ごとに対象集合を分ける（診断なしは success のみ、
  冪等性と可逆性は全件）。現状は前者に合わせて一律に絞っている。

## L-008: BLANK_LINE-1 の `package` / `use` グループの空行を実装していない

- **逸脱**: formatting.md BLANK_LINE-1 は「`package`, `use`, `no` 文: 文のグループの前後
  （ただし `package` 直後の `use` など、関連する宣言が続く場合は除く）」に空行を入れると定めるが、
  実装していない。同項目の `sub` 定義・フェーズブロック・POD・`__DATA__` は実装済み。
- **ADR の記述**: ADR 0008 は冒頭で「formatting.md を仕様とする」と述べており、
  §4 で「自動空行挿入（sub 前後等, BLANK_LINE-1）は build 時に `BlankLine` を置くことで表現する」と書いている。
- **理由**: 「関連する宣言が続く場合は除く」の判定が仕様として確定していない。
  `package Foo; use strict; use warnings;` を1グループと見るのは明らかだが、
  `use` の間に `my $x = 1;` が挟まったとき、`require` や `no` が混ざったとき、
  条件付き `use if` があるときの境界が書かれていない。
  推測で実装すると、後で仕様を確定したときに fixture を二度書き換えることになる。
- **影響範囲**: `use` 文の連なりの前後に空行が入らない。既存 fixture では
  `package Foo::Bar;` と `use strict;` が隣接する形しか出てこないため、
  スナップショットへの影響は現時点ではない。
- **原状回復**: `wants_preceding_blank_line` / `wants_surrounding_blank_lines`
  （`src/fmt/build.rs`）にグループ判定を足す。空行の抑制はレンダラ側にあるので、
  builder は「グループの先頭か」を判定できればよい。
  ただし先に formatting.md 側で境界を確定すること。

## L-009: fixture を Perl として正しい形に書き換えた

- **逸脱**: 評価ノート付録 C は fixture を「仕様として維持 / 新設計で不要 / 挙動を意図的に変更」の
  3つに分類せよと言うが、実際に必要だった4つ目の分類は「**そもそも Perl ではない**」だった。
  該当する 10 本を、意図を保ったまま perl の通る形に書き換えた。
- **評価ノートの記述**: 付録 C
- **理由**: Perl でないものは「Perl をどう整形するか」の仕様になりえない。
  たとえば `sub placeholder_only($,@,%)` は slurpy が2つあり signature として不正で、
  perl は prototype として読む。それを signature とみなして整形すれば prototype の
  文字列が書き換わる。fixture がその出力を「正解」として固定していた。
- **影響範囲**: 書き換えた 10 本のスナップショットが変わる。
  内容は `notes/2026-07-28-redesign-snapshot-classification.md` と
  `notes/2026-07-28-redesign-migration-status.md` §6.2 に記録。
- **原状回復**: 不要。ただし「fixture は perl が通ること」を
  `scripts/perl-check` で常時検査しているので、この分類が再発しないことは担保されている。

## L-010: lexer の脱出ハッチは `take_name` だけではない

- **逸脱**: L-005 は `Lexer::take_name()` を「3つ目の expect 状態を作らない代わりの
  1回限りの命令」として記録したが、実装には同型のものが他に3つある。
  - `take_caret_name()` — `${^MATCH}` の `^NAME` を1トークンとして読む。
    ブレースを挟むためスキャナはキャレットを通常の演算子位置で見てしまい、
    ビット排他和として読む。2トークンになると `${^ MATCH}` と
    `${^MATCH}` を出力で区別できなくなる（別の変数である）。
  - `take_sigil()` — シグネチャのプレースホルダ `sub f($, $y)` の裸の `$`。
    `Term` では次の文字を名前として読もうとする。呼び出し箇所は2つ
    （`grammar::primary::variable` と signature 解析）。
  - `peek_raw_paren_body()` / `take_raw_parens()` — prototype と属性引数の
    `(...)` を中身を解釈せずに読む。ADR 0004 §5 の「kind 付き raw span」そのもの。
- **ADR の記述**: ADR 0005 §2「`pub enum Expect { Term, Operator }`」
- **理由**: L-005 と同じ。名前・裸のシグル・raw span はいずれも2状態のどちらでも
  正しく表現できない位置であり、`take_raw_parens` は ADR 0004 §5 が明示的に認めている。
- **影響範囲**: lexer API に「parser が読み方を指定する」入口が計4つある。
  ADR 0007 §5 の「強制は1箇所」規約が守られているのは `take_name` のみで、
  他の3つは呼び出し箇所が固定されているだけである（それぞれ2, 2, 2箇所）。
- **原状回復**: expect に `Name` を足せば `take_name` と `take_caret_name` は消える。
  `take_sigil` と raw span は消えない。

## L-011: 組み込みテーブルは生成するが、ビルド時ではない

- **逸脱**: ADR 0007 §6 は組み込み関数表を「perl の実 prototype からビルド時に生成する
  （約200関数）」と定める。実装では `scripts/generate-builtins` が
  `prototype("CORE::$name")` から生成し、その**出力をコミット**している。
- **ADR の記述**: ADR 0007 §6
- **理由**: ビルド時生成は crate のビルドに perl のインストールを要求する。
  「perl が無いとビルドできない Rust crate」より
  「perl が組み込みを増やしたら再生成が要る表」のほうが割に合う。
  写像は perl 自身のもの（toke.c）: 引数0個は FUNC0、ちょうど1個は UNIOP、
  それ以外は LSTOP。prototype が `undef` の組み込みは perl の文法側に固有の構文を持つ
  ものだけで、スクリプト内に理由付きで手書きしてある。
- **影響範囲**: perl のバージョンが変わって組み込みが増減したとき、
  再生成しない限り表が古くなる。再生成は `scripts/generate-builtins` を実行して
  `src/parse/grammar/builtins.rs` の `match` 本体を差し替え、`cargo fmt` を掛けるだけ。
- **原状回復**: `build.rs` から同じスクリプトを走らせる。perl を必須依存にする判断が要る。
- **経緯**: この逸脱が記録されていなかった間、表は手書きの約140エントリだった。
  `eval` が欠けており、`eval <<EOT` が左シフトとして字句解析され、
  heredoc 本体がコードに昇格していた（`URI::data`）。

## L-012: `balanced_paren_body_len` はクォートをスキップしない

- **逸脱**: doc コメントは「`sub f("(")` が深さ計算を狂わせないようクォート部分を
  スキップする」と主張していたが、実装していなかった。
- **ADR の記述**: なし（実装内のコメントと実装の不一致）
- **理由**: 実装を doc に合わせるのではなく、doc を実装に合わせた。
  この関数が読むのは prototype だけで、prototype に文字列は入らない。
  `sub f("(")` は perl も "Prototype not terminated" で拒否する。
  括弧を含む文字列がありうるのは signature のデフォルト値
  （`sub f($x = "(")`）だが、そちらは signature としての解釈が先に成功するので
  この関数には到達しない。クォートをスキップすれば
  **perl が拒否する入力を camello が受理する**ことになり、
  それは `scan_delimited_content` が文字クラスについて明示的に拒否している取引と同じである。
- **影響範囲**: なし（挙動は変えていない）。
- **原状回復**: 不要。

## L-013: パーサに深さ上限を入れた

- **逸脱**: ADR 0007 は入力の深さに上限を設けていない。実装では開いたマーカー数が
  512 を超えた時点で診断を出し、残りを1つの ERROR ノードに収めて停止する。
- **ADR の記述**: ADR 0007 §3「回復はパニックモード」（上限の記述はない）
- **理由**: 再帰下降パーサと再帰的な formatter のウォークは、いずれも入力の深さに
  比例したスタックを使う。formatter は深さ約3500でスタックを使い切っていた。
  上限が無いということは「十分に深い入力でプロセスが落ちる」ということで、
  それは診断ではない。上限を parser 側に置いたのは、診断を出せるのが parser で、
  parser が作る木を formatter が歩くので、木を抑えれば下流すべてが抑えられるため。
  512 は手書きの Perl のどれよりも深く、スタックが尽きる深さよりはるかに浅い。
- **影響範囲**: 512 段を超えてネストした入力は整形されず、そのまま複製される。
  `@INC` 配下 758 本のコーパスで到達したファイルは 0 本。
- **原状回復**: `fmt::build` と `fmt::render` の再帰を明示スタックに書き換え、
  parser 側も同様にすれば上限を外せる。

## L-014: `format` 宣言を原子的な実行列として字句解析する

- **逸脱**: ADR 0005 §3 が原子的実行列として挙げるのは quote-like 演算子、
  heredoc 本体、POD、`__DATA__` の4つ。実装ではこれに `format NAME = ... .` を加えた。
- **ADR の記述**: ADR 0005 §3
- **理由**: picture 行は式でも文でもない。`@<<<<` は左詰め5桁のフィールドであり、
  式として解析して整形し直すと `@< << <` になる（意味を持たない4つのトークン）。
  ADR 0005 §3 の基準は「スキャンモードを切り替える構文」であり、
  `format` はまさにそれに当たる。
- **影響範囲**: `format` は宣言が続く位置でのみキーワードになる。
  `(format => 1)`、`$obj->format($x)`、`sub format {}` は従来どおり。
- **原状回復**: 不要。ADR 0005 §3 の列挙に追記するのが筋。

## L-015: 継続インデントは行ではなくスコープが持つ

- **逸脱**: ADR 0008 §2 の Doc IR には `Indent` しかなく、継続インデント
  （formatting.md INDENT-3）は「改行した次の1行に4スペース足す」renderer 内の
  フラグとして実装されていた。実装に `Doc::Continuation` を加えた。
- **ADR の記述**: ADR 0008 §2（Doc IR の構成要素）、§3(2)
- **理由**: 行単位のフラグは `Indent` と合成できない。ユーザ改行で折り返した
  引数リストの中で `[` が改行すると、その中身は `[` 自身より深くならず、
  閉じ括弧 `] ) )` は最後の要素の末尾に畳まれて、どれがどれを閉じるのか
  出力から読めなくなっていた（`nested_call_argument_indent`）。
  スコープにすると、(1) 中に入れ子になった `Indent` はその1段深くから数え、
  (2) スコープの外に出す閉じ括弧は構文が始まった桁に戻る、の2つが同時に成立する。
  スコープは flat な括弧の中身だけに張る。文全体に張ると、折り返した条件式や
  シグネチャの後に続くブロックの本体まで1段深くなる。
- **影響範囲**: 括弧の外での折り返し（二項演算子・後置修飾子・`=>` の値）は
  従来どおり1行フラグのまま。括弧の中で折り返した場合のみ深さが累積する。
- **原状回復**: `Doc::Continuation` を剥がして `UserLine` を元のフラグに戻せばよいが、
  上記の欠陥が戻る。

## L-016: アライメントの上限はグループが持つ

- **逸脱**: `max_alignment_padding` は「1行が受け取るパディングの上限」だったが、
  「グループ内のアンカーの桁差の上限」に変えた。既定値 40 → 64。
- **ADR の記述**: ADR 0008 §5、formatting.md §7（ALIGNMENT-3 として追記）
- **理由**: 行ごとに切り詰めると、同じグループの各行が別々の桁に並ぶ。
  それは「揃っている」でも「揃えない」でもなく、しかも再フォーマットで
  直らない（`align_columns_disagree`）。グループは一つの桁で揃うか、
  まったく揃わないかのどちらかであるべき。
- **影響範囲**: 桁差が上限を超えるグループは、以前は部分的に揃っていたが、
  これからは一つも揃わない。既定値を上げたため、Test2 の `object { call ... }`
  程度の幅は従来どおり揃う。
- **原状回復**: `align_class` のガードを `pad_to` 側の `min` に戻す。

## L-017: 括弧の内側の空白は要素数ではなく中身で決まる

- **逸脱**: formatting.md SPACING-7 の Standard は「要素が2つ以上のときだけ
  内側にスペース」だった。「単純項ひとつのときだけ密着」に変えた。
  デリファレンスの波括弧も同じ規則に従わせた。
- **ADR の記述**: formatting.md SPACING-7（本文を書き換え）
- **理由**: 要素数で決めると `[ map { $_->foo } @$list ]`、`{ $obj->qux }`、
  `[ foo($body) ]` が「1要素」として潰れる。規則が意図していたのは `[$x]` であって、
  構造を持つものを括弧に押し付けることではなかった。
- **影響範囲**: `${^MATCH}` は密着し続けなければならない——波括弧の中身は
  キャレットを含む1つの名前で、スペースを入れると**別の変数になる**。
  トークン列は同一で `perl -c` も `B::Deparse` も通るため、これを見つけられるのは
  スナップショットだけである（`scripts/perl-check` の doc コメントが言う盲点）。
- **原状回復**: `delimited` の `spacious` を `item_count(node) >= 2` に戻す。
